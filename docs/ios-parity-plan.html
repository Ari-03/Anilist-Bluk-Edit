1. TL;DR

All five "iOS is ahead" claims check out against the web code, and the aliased-batch caution is accurate. Two of the proposed additions (a sync-age guard, 5xx retry) already exist on web, so the iOS side is actually porting those from us. The real prize is one structural change: a single request pacer that every AniList call goes through, fed by the rate-limit headers the proxy currently throws away. Everything else (cancellation, per-alias results, verification, aliased deletes) hangs off that one seam.

2. Health check: what happened when I ran the app

Static health is fine. tsc --noEmit, eslint . and next build all pass on Next 16.3 / Node 26.8 (engines say 24.x; no issue either way). The login screen and the authenticated shell both render. The trouble is at runtime, and it is exactly the class of problem the iOS notes describe.

The sequence from the dev server log

I started next dev on port 3491 and opened it in the preview. You clicked "Log in with AniList" (the preview is shared, so I saw the OAuth redirect happen twice), completed OAuth, and landed on /auth/callback. Then:

GET  /auth/callback           200

So the app is not broken in the usual sense. Your IP was being rate-limited by AniList (very plausibly because the iOS app was running bulk work at the same time; the 30/min budget is per IP, not per app), and three code paths turn a transient 429 into something that looks like a broken app:

  1. Session validation logs you out on any upstream failure. src/pages/api/auth/session.ts:69–84 clears the cookie whenever !response.ok, including 429 and 5xx. A rate limit should never invalidate a session.
  2. The proxy masks non-JSON upstream bodies as HTTP 500. src/pages/api/anilist/graphql.ts:35 calls response.json() before checking status. Cloudflare's 429 page is HTML, so the browser sees a 500 with no Retry-After, and the limiter treats it as a generic server error (2 s / 4 s / 8 s backoff, then gives up).
  3. Callback's "Back to Login" is a dead link. src/pages/auth/callback.tsx:90 pushes /login; the login screen lives at /.

Smaller things I noticed

  • Hot reload is dead when you open the dev server as 127.0.0.1 (which the T3 preview does). Next 16 blocks the HMR websocket and the dev font as cross-origin; the console fills with ws://…/_next/hmr failed. Fix is one line: allowedDevOrigins: ['127.0.0.1'].
  • next dev on Next 16 now writes AGENTS.md and CLAUDE.md into the repo on every start. CLAUDE.md is git-ignored, AGENTS.md is not. Either commit it or set agentRules: false.
  • next.config.js still lists antd and the rc-* packages in transpilePackages; antd was removed in July. Harmless, but stale.
  • The last_token_validation guard in AuthContext can never fire on mount (it requires user && accessToken, which are always null at that point), so every page load spends one request of the 30/min budget on /api/auth/session. Not urgent, but it matters more once the pacer exists.
  • AniList's X-RateLimit-Limit header now reports 30, not the 90 the iOS comment mentions (checked with an unauthenticated probe today). The "only ever slow down" rule in the iOS pacer is still the right rule, but the headers are currently trustworthy.

3. Claim-by-claim verification

3.1 Rate-limit handling

Claim
Proxy strips Retry-After and X-RateLimit-*; web retries 2 s, 4 s, 8 s and gives up.
Evidence
graphql.ts:36–46 only forwards the JSON body. rateLimiter.ts:79–86 computes baseDelay = 1000 / 0.5 = 2000 then × 2^retry for maxRetries = 3. Total wait ≈ 14 s against a 60 s window.
Verdict
Confirmed, and understated. The HTML-body case above means the client often never even sees a 429.

3.2 Limiter scope

Claim
A fresh limiter per bulk run; the pre-run refetch and other in-flight requests are invisible to it.
Evidence
useBulkOperations.ts:163, 262 new RateLimiter(config) per run. The custom-list refetch at :144 goes through store.fetchMediaLists, which builds its own bare AniListClient (store/index.ts:462). Quick edits (MediaListView.tsx:77,94) and session validation use no limiter. relationDiscovery.ts:65 has yet another private RateLimiter.
Verdict
Confirmed. Five independent request sources share one 30/min budget and none of them know about each other.

3.3 Cancellation

Claim
Stop is a flag checked between chunks.
Evidence
useBulkOperations.ts:175, 273 check cancelRef.current at the top of each loop iteration. RateLimiter.stop() sets stopped = true and empties the queue, but executeWithRetry never reads stopped, so a request mid-backoff keeps retrying after Stop. The toast literally says "the current batch will finish first".
Verdict
Confirmed. Worst case today: Stop during a 429 backoff waits the full 14 s and still sends.

3.4 Fast-path verification

Claim
Web merges whatever comes back and counts everything as success.
Evidence
useBulkOperations.ts:230–235: mergeMediaListEntries(results) then succeededIds.push(...allIds), no intersection. Separately, the mutation's selection set (anilist.ts:339–350) is id mediaId status score progress updatedAt, so a bulk "set private" or "set notes" or "hide from status lists" is applied on the server but never reflected in the store until a full refetch.
Verdict
Confirmed, plus a settled-updates bug. This one contradicts the July design goal ("never refetch") for three of the six bulk fields.

3.5 Input validation

Claim
iOS validates score against format and step; web parses loosely.
Evidence
useBulkOperations.ts:78–79: parseFloat(options.score), parseInt(options.progress). The inputs carry min/max/step attributes but nothing enforces them because there is no form submit. parseFloat("abc") becomes NaN, which JSON-serialises to null and is sent. QuickEditForm.tsx:59,71 does parseFloat(v) || 0: clearing the field to retype sets the score to 0 and the input snaps back to "0".
Verdict
Confirmed. Port the iOS BulkEditInput rules as a pure function used by both forms.

3.6 The aliased-batch caution

Claim
Web throws on any errors array, so one bad alias fails all ten and only idempotent retries save you.
Evidence
anilist.ts:65–69 throws when data.errors exists, discarding partial data.data. useBulkOperations.ts:194–205 marks the whole chunk failed. "Retry failed" then re-sends all ten, nine of which already succeeded.
Verdict
Confirmed.

3.7 Things iOS proposed that web already has

  • Sync-age guard. useBulkOperations.ts:135–155 refetches when lastDataLoad is older than five minutes before any custom-list edit. iOS is adopting our approach; nothing to port back.
  • 5xx retry. rateLimiter.ts:101–104 retries 500/502/503/504 with backoff. Keep this behaviour but it should live in the client so every caller gets it, not just bulk runs.

4. Target architecture

Today, request pacing is a decoration bolted onto two call sites. The change is to make it a property of the client so it is impossible to bypass. Everything that talks to AniList already funnels through AniListClient.request; that is the seam.

Callersbulk hook · store.fetchMediaLists · quick edit · relation finder · refreshUser
AniListClient.requestreserve slot → sleep(signal) → fetch(signal) → observe headers → retry 429 / 5xx
pacer (singleton)token bucket 30/min, burst 3, penalty horizon; only ever slows down
/api/anilist/graphqlforwards status + Retry-After + X-RateLimit-* ; text body fallback
AniListgraphql.anilist.co

Two properties fall out of this shape:

  • One budget. The refetch, a quick edit and a bulk chunk all draw from the same bucket, and a 429 seen by any of them pushes every pending slot past Retry-After.
  • Cancellation is free. The AbortSignal passed to request aborts the pacer sleep and the fetch. The bulk hook owns one AbortController per run; Stop calls abort().

Why keep the proxy at all?

It is tempting to call AniList straight from the browser like iOS does. Two reasons not to: AniList's CORS policy exposes the X-RateLimit-* headers but not Retry-After (checked today via access-control-expose-headers), and the proxy keeps the token out of every request body on the wire to third parties. So we keep the proxy and make it transparent instead.

Phase 0 · Stop the bleeding ship first

Small, mechanical, and it fixes what you hit today.

Changes

  • Proxy src/pages/api/anilist/graphql.ts: read text(), try to parse, forward upstream status and the four rate-limit headers, and turn non-JSON bodies into a GraphQL-shaped error with the real status.
  • Session route src/pages/api/auth/session.ts: only clear the cookie on a definitive auth failure (401, or GraphQL status: 400/401 "Invalid token"). On 429/5xx/HTML respond 200 with the cached session and stale: true, exactly as the timeout branch already does.
  • Callback src/pages/auth/callback.tsx:90: router.push('/').
  • next.config.js: allowedDevOrigins: ['127.0.0.1'], agentRules: false (or commit AGENTS.md), drop the antd transpilePackages.

Proxy sketch

const RATE_HEADERS = ['retry-after', 'x-ratelimit-limit', 'x-ratelimit-remaining', 'x-ratelimit-reset'] as const

const upstream = await fetch(ANILIST_URL, { method: 'POST', headers, body })
for (const name of RATE_HEADERS) {
  const value = upstream.headers.get(name)
  if (value) res.setHeader(name, value)
}
const text = await upstream.text()
const body = parseJson(text) ?? {
  data: null,
  errors: [{ message: `AniList returned ${upstream.status} ${upstream.statusText}`, status: upstream.status }],

return res.status(upstream.status).json(body)

  • Session validation during a 429 keeps the cookie and returns the cached user.
  • Opening http://127.0.0.1:<port> in dev has working HMR and no websocket errors.

Phase 1 · One pacer, inside the client

Port RequestPacer.swift almost verbatim; it is 60 lines and already has the right unit tests to copy. Then move the retry loop from RateLimiter into AniListClient.request and delete RateLimiter.

New file src/lib/pacer.ts

/** Token-bucket pacer shared by every AniList request in the tab. Headers only ever slow it down. */
export class Pacer {
  private tokens: number
  private anchor = 0            // last refill time, or the penalty horizon when pushed into the future
  private lastNow = 0

  constructor(private readonly perMinute = 30, private readonly burst = 3) {
    this.tokens = burst
  }

  /** Reserve the next send slot. Returns the epoch-ms the caller must wait until. Synchronous on purpose. */
  reserve(now = Date.now()): number {
    this.lastNow = Math.max(this.lastNow, now)
    const base = Math.max(now, this.anchor)
    this.tokens = Math.min(this.burst, this.tokens + ((base - this.anchor) / 1000) * (this.perMinute / 60))
    if (this.tokens >= 1) { this.tokens -= 1; this.anchor = base; return base }
    const wait = ((1 - this.tokens) / (this.perMinute / 60)) * 1000
    this.tokens = 0
    this.anchor = base + wait
    return this.anchor
  }

  /** Push every future slot past `until` (429 Retry-After, or remaining ≤ 2). */
  penalize(until: number) {
    if (until <= Math.max(this.anchor, this.lastNow)) return
    this.anchor = until
    this.tokens = 0
  }

  /** Feed response headers. Uses Retry-After on 429 and X-RateLimit-Remaining/Reset otherwise. */
  observe(status: number, headers: Headers, now = Date.now()) {
    if (status === 429) {
      const seconds = Number(headers.get('retry-after') ?? 60)
      this.penalize(now + (Number.isFinite(seconds) ? seconds : 60) * 1000 + 1000)
      return
    }
    const remaining = Number(headers.get('x-ratelimit-remaining'))
    const reset = Number(headers.get('x-ratelimit-reset'))
    if (remaining <= 2 && Number.isFinite(reset)) this.penalize(reset * 1000 + 1000)
  }
}

export const pacer = new Pacer()

Client request loop src/lib/anilist.ts

interface RequestOptions {
  signal?: AbortSignal
  retryTransient?: boolean   // queries and idempotent mutations opt in
}

private async request<T>(query: string, variables?: Variables, opts: RequestOptions = {}): Promise<GraphQLBody<T>> {
  for (let rateLimitRetries = 0, transientRetries = 0; ; ) {
    await sleepUntil(pacer.reserve(), opts.signal)      // rejects with AbortError on cancel
    const res = await fetch('/api/anilist/graphql', { method: 'POST', body: ..., signal: opts.signal })
    pacer.observe(res.status, res.headers)

    if (res.status === 429 && rateLimitRetries++ < 2) continue          // pacer already holds the horizon
    if (res.status >= 500 && opts.retryTransient && transientRetries++ < 1) {
      await sleepUntil(Date.now() + 1000, opts.signal); continue
    }
    const body = (await res.json()) as GraphQLBody<T>
    if (!res.ok && !body.data) throw new AniListRequestError(res.status, body.errors)
    return body                                           // callers decide what a partial body means
  }
}

The loop mirrors AniListAPI.execute on iOS: reserve before any await, re-check after sleeping, penalise on 429, one transient retry only for opted-in calls. Because observe runs on every response, a 429 seen by a quick edit slows the bulk run that is about to fire, which is the "shared" property we want.

What gets deleted

  • src/lib/rateLimiter.ts entirely.
  • The private limiter in src/lib/relationDiscovery.ts; it just calls the client now.
  • rateLimiterRef, rateLimiterConfig, setRateLimiterConfig and RateLimiterStats plumbing in the hook and BulkEditForm.

What replaces the four knobs

Requests/second, concurrency, max retries and retry delay all become meaningless once the server tells us the budget. The "Advanced · rate limiting" panel becomes a read-only line: "AniList allows 30 requests/min · 27 left · next send in 1.4 s", driven by a tiny useSyncExternalStore over the pacer. If you want one knob, keep "requests per minute" capped at 90, but I would ship with none.

Acceptance

  • bun test passes the ported pacer tests: burst is immediate, sustained converges to 2 s, refill over time, penalty pushes all slots, past penalty ignored, low-remaining header penalises, healthy header does not.
  • Manual: run a bulk update, then immediately hit the header refresh button; the refetch waits for a slot instead of triggering a 429.

Phase 2 · Per-alias results and fast-path verification

Make the client return partial data, split it per alias, and make the hook settle entries individually.

Alias splitter src/lib/anilist.ts

type AliasResult<T> =
  | { alias: string; ok: true; data: T }
  | { alias: string; ok: false; message: string }

/** Turn a partially-failed aliased response into one result per alias. Uses error.path when AniList sets it. */
function splitAliases<T>(body: GraphQLBody<Record<string, T | null>>, aliases: string[]): AliasResult<T>[] {
  const byPath = new Map(body.errors?.flatMap(e => (typeof e.path?.[0] === 'string' ? [[e.path[0], e.message]] : [])) ?? [])
  const fallback = body.errors?.[0]?.message ?? 'No result returned'
  return aliases.map(alias => {
    const data = body.data?.[alias]
    return data ? { alias, ok: true, data } : { alias, ok: false, message: byPath.get(alias) ?? fallback }
  })
}

bulkSaveMediaListEntries returns AliasResult<MediaList>[] keyed back to mediaId. If body.data is entirely null (auth or 429 after retries), request already threw, so the chunk fails as a unit only when it truly did.

Phase 3 · Aliased deletes

Same trick as saves. Bulk-deleting 200 entries drops from 200 requests (~7 min at 30/min) to 20.

async bulkDeleteMediaListEntries(ids: number[], opts?: RequestOptions) {
  const defs = ids.map((_, i) => `$id${i}: Int!`).join(', ')
  const fields = ids.map((_, i) => `d${i}: DeleteMediaListEntry(id: $id${i}) { deleted }`).join('\n')
  const body = await this.request<Record<string, { deleted: boolean } | null>>(
    `mutation (${defs}) { ${fields} }`,
    Object.fromEntries(ids.map((id, i) => [`id${i}`, id])),
    opts,
  )
  return splitAliases(body, ids.map((_, i) => `d${i}`)).map((r, i) => ({ id: ids[i], ...r }))
}

runBulkDelete becomes the same chunk-of-10 loop as updates, removing confirmed IDs from the store per alias. Deletes are not idempotent in the same sense (a second delete of a gone entry errors), so treat "not found" as success on retry.

Phase 4 · Real cancellation

  • The hook creates new AbortController() per run and passes signal to every client call.
  • cancel() calls abort(); sleepUntil rejects immediately, so Stop takes effect during a pacer wait or a 429 penalty, not after it.
  • In-flight request: I recommend not aborting the fetch itself. Once the request has left, AniList will apply it whether or not we listen, and aborting turns a known outcome into an unknown one. Let the one in-flight chunk settle (≈1 s), then stop. iOS aborts the URLSession task and marks the rest failed; on web the "let it land" version is both simpler and more honest. See decision D2.
  • Entries never attempted go back to null sync state, as today. The "Cancelling — the current batch will finish first" toast becomes accurate instead of aspirational.

Phase 5 · Input validation

Port BulkEditInput.swift as a pure function next to getScoreRange:

// src/lib/scoreFormat.ts
export type ParsedEdit =
  | { ok: true; score?: number; progress?: number }
  | { ok: false; field: 'score' | 'progress'; message: string }

export function parseEditInput(scoreText: string, progressText: string, format: ScoreFormat | undefined): ParsedEdit {
  const { max, step } = getScoreRange(format)
  const s = scoreText.trim().replace(',', '.')
  const p = progressText.trim()
  let score: number | undefined
  if (s) {
    score = Number(s)
    const onStep = Math.abs(score / step - Math.round(score / step)) < 1e-6
    if (!Number.isFinite(score) || score < 0 || score > max || !onStep)
      return { ok: false, field: 'score', message: `Score must be 0–${max} in steps of ${step}` }
  }
  let progress: number | undefined
  if (p) {
    progress = Number(p)
    if (!Number.isInteger(progress) || progress < 0)
      return { ok: false, field: 'progress', message: 'Progress must be a whole number ≥ 0' }
  }
  return { ok: true, score, progress }
}
  • BulkEditForm shows the message under the field and disables Apply while !ok.
  • QuickEditForm keeps raw strings in local state and parses on save, which also fixes the "cleared field becomes 0" snap-back.
  • Unit tests: one per format for max and step (POINT_10_DECIMAL accepts 8.5, rejects 8.55; POINT_5 rejects 6; POINT_100 accepts 100).

6. What not to port from iOS

iOS pieceWhy leave it
SwiftData sync service, watermarks, incremental ingestWeb holds the whole list in memory and a full refetch is two requests. The five-minute freshness window already does the job.
penaltyVersion re-loop after sleepingNeeded on iOS because the actor is released during Task.sleep. In JS the loop simply calls reserve() again after waking; same guarantee, no version counter.
customLists(asArray: true)The store, filters and card chips all consume the { name: boolean } map form. Changing the wire shape would touch far more than it saves.
Entry-by-entry SaveMediaListEntry for custom listsWeb's aliased 10-per-request batch is strictly better once per-alias results exist. iOS should adopt ours, which is what its notes say.
Session generation counterOnly needed because the iOS client is a long-lived singleton across logins. On web the client is rebuilt per token in index.tsx.
